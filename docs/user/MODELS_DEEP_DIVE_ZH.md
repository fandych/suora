# Suora Models 深度迭代手册（30 个落地点）

这份手册把 `Models` 模块收敛成 30 个真实落地点，重点是 provider、model、比较、稳定性和密钥边界。

## 1. 基础认知

1. 把 provider 和 model 分开理解。
2. 把运行时支持和 UI 暴露分开理解。
3. 把连通性问题和能力问题分开处理。
4. 把本地模型和云模型分开评估。
5. 把 OpenAI-compatible 当作协议层，而不是具体厂商名。

## 2. 配置路径

6. 先建 provider，再启用 model。
7. 保存 provider 后立刻做连接测试。
8. 连接通过后再回其他模块使用。
9. 只启用真正会用到的模型。
10. provider 名称应能让你一眼区分用途。

## 3. 模型选择

11. 高复杂任务优先稳定能力。
12. 高频草稿任务优先成本和速度。
13. 附件任务额外看模态支持。
14. 长上下文任务额外看窗口表现。
15. Compare 结果应反映真实任务，而不是空泛印象。

## 4. 稳定性与成本

16. 不要默认最强模型处理所有任务。
17. 不要忽视速率限制和网络抖动的影响。
18. 对关键流程预留备用 provider 更稳。
19. 对低价值任务下调模型成本档位。
20. 对高价值输出允许使用更强模型，但要解释原因。

## 5. 安全与边界

21. API Key 是最敏感配置对象。
22. Base URL 错误不仅会失败，也可能打到错误环境。
23. Secure Storage 警告必须被认真对待。
24. 内存态密钥适合临时使用，不适合长期依赖。
25. 模型配置应避免散落在多个地方形成双重真相。

## 6. 排障与治理

26. Chat 失败先回 Models 验证当前模型是否可用。
27. Agent 失常时不要忘记排查模型本身。
28. Provider 列表过长时应做清理和归类。
29. 长期失效或无人使用的模型应停用。
30. 好的 Models 治理最终目标是稳定、清楚、可切换、可控成本。
