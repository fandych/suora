# Suora Pipeline 深度迭代手册（30 个落地点）

这份手册把 `Pipeline` 模块单独展开成 30 个真实落地点，重点是把“多步流程设计”变成可运行、可排障、可持续维护的资产。

## 1. 进入 Pipeline 前

1. 先确认这是不是重复流程，而不是一次性聊天任务。
2. 先确认相关 Agent 已可用。
3. 先确认相关模型已经启用。
4. 先写出目标产物，而不是先堆很多步骤。
5. 先决定这条流程未来是手动触发还是定时触发。

## 2. 步骤设计

6. 每个步骤只承担一个明确任务。
7. 每个步骤都应能说清输入和输出。
8. 优先用自然顺序组织步骤，而不是过早设计复杂分支。
9. 对高风险步骤单独设置更清楚的提示词。
10. 对依赖外部工具的步骤预留超时与重试空间。

## 3. 变量与条件

11. 用变量承接前一步结果，而不是手写复制粘贴内容。
12. 变量命名应反映业务意义，而不是只写 `result1`。
13. `runIf` 只用于真正有条件分支的地方。
14. 条件表达式应先可读，再谈复杂性。
15. 变量默认值只在确有必要时提供，避免掩盖输入缺失。

## 4. 执行与观察

16. 先做 dry run 再做真实运行。
17. 真实运行后优先看步骤状态，再看总体结论。
18. 历史记录应作为调试入口，而不是事后摆设。
19. Mermaid 预览先看结构是否合理，再看文案是否漂亮。
20. 看到 fallback 信息时，优先理解降级原因，不要忽略它。

## 5. 协作与安全

21. Chat 适合触发 Pipeline，但不适合长期替代 Pipeline。
22. Timer 适合调度 Pipeline，但必须先用手动运行验证成功。
23. Agent 权限越宽，步骤越应保持单一职责。
24. 流程里涉及敏感资料时，优先收紧上下文范围。
25. 成本敏感流程必须显式设置预算上限。

## 6. 治理与维护

26. 大改步骤前先导出备份。
27. 重复失败的步骤应先回到 Agent 或 Models 查根因。
28. 一条流程变太长时应考虑拆成两条。
29. 执行历史里长期无人看的流程应考虑归档或删除。
30. 好的 Pipeline 最终应做到输入清楚、历史可读、失败可修、成本可控。
