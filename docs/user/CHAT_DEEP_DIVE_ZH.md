# Suora Chat 深度迭代手册（10 轮 × 每轮 30 问）

这是一份超细版样板文档，用来展示如何把单个模块继续展开成更高密度的问题驱动手册。当前选择 `Chat` 作为第一份深挖模块，因为它是大多数真实任务的第一入口，也是和 Models、Agents、Documents、Pipeline 连接最紧的工作面。

## 第 1 轮：进入 Chat 之前

1. 问：Chat 在整个工作台里的定位是什么？答：它是日常任务执行的主入口，而不是单纯展示回复的窗口。
2. 问：为什么大多数用户第一站不是 Settings？答：因为真实价值通常先在 Chat 里被感知，然后才反向暴露配置问题。
3. 问：为什么 Chat 之前常要先去 Models？答：没有可用模型时，Chat 只能显示界面，无法完成真正的 AI 调用。
4. 问：进入 Chat 前必须配置 provider 吗？答：如果你希望得到真实回复，就必须至少配置一个 provider 或本地模型端点。
5. 问：只配置 provider 不启用模型够吗？答：不够，provider 只是连接入口，模型启用后才是可执行能力。
6. 问：为什么要先理解 Agent 再聊天？答：因为同一个问题在不同 Agent 下会触发完全不同的角色和工具策略。
7. 问：Chat 页面对新手最容易误导的点是什么？答：界面能打开不代表工作台已经真正可用。
8. 问：第一次看到 Chat 时最先看什么？答：先看会话列表，再看当前会话绑定的模型和 Agent。
9. 问：为什么当前会话的 Agent 很关键？答：它决定系统提示、技能绑定和工具边界。
10. 问：为什么当前会话的模型也同样关键？答：它决定推理质量、成本、速度和模态能力。
11. 问：进入 Chat 前需要先读历史会话吗？答：如果你复用旧线程，就应该先看上下文是否仍然适合当前任务。
12. 问：为什么不建议所有任务都塞进一个老会话？答：上下文会漂移，模型会被历史噪声持续污染。
13. 问：什么情况下应该新建会话？答：当任务目标、角色或资料边界已经和旧线程不同。
14. 问：什么情况下保留原会话更好？答：当你仍在延续同一问题链条，需要上下文连续性。
15. 问：Chat 和 Documents 的边界在哪里？答：短时交互留在 Chat，长期知识沉淀放进 Documents。
16. 问：Chat 和 Pipeline 的边界在哪里？答：一次性任务在 Chat，重复流程在 Pipeline。
17. 问：Chat 和 Timer 的边界在哪里？答：立即执行在 Chat，按时间触发在 Timer。
18. 问：Chat 和 Channels 的边界在哪里？答：桌面内对话在 Chat，外部消息入口在 Channels。
19. 问：为什么先知道这些边界有价值？答：因为它能让你少走很多“这个模块也能勉强做”的弯路。
20. 问：第一次使用 Chat 前最推荐的准备顺序是什么？答：Models、Agents、Chat，然后才是 Documents、Pipeline 和其他模块。
21. 问：如果你只想快速试一下，最小准备是什么？答：一个 provider、一个 enabled model、一个默认 Agent。
22. 问：初始 Agent 不确定时应该选哪个？答：先选 Assistant，再根据失败样式决定是否切换专业 Agent。
23. 问：初始模型不确定时应该怎么选？答：先选稳定、延迟可接受、成本可控的模型，而不是一味追求最强。
24. 问：第一次进入 Chat 时需要先看日志吗？答：通常不需要，除非启动时已经出现明显错误提示。
25. 问：Secure Storage 警告和 Chat 有什么早期关系？答：它会直接影响模型密钥是否能在重启后继续可用。
26. 问：为什么要在第一次任务前确认警告？答：否则你会把“重启后密钥丢失”误判为模型或网络问题。
27. 问：首次进入 Chat 应该先跑什么任务？答：先跑一个短而清晰的基础问题，验证回复链路是否正常。
28. 问：为什么不建议第一次就喂复杂附件？答：你还没验证模型、Agent、权限和流式回复是否已经稳定。
29. 问：第一次成功的标准是什么？答：能稳定收到正确的流式回复，并确认当前 Agent 与模型选择生效。
30. 问：进入 Chat 前这一轮最该记住什么？答：Chat 是工作入口，但是否好用主要取决于它前面的模型和 Agent 准备是否到位。

## 第 2 轮：会话与线程管理

1. 问：会话在 Chat 里扮演什么角色？答：它是消息、上下文和后续追问的持久化容器。
2. 问：为什么会话管理比单条消息更重要？答：因为模型真正看到的是整个线程，而不是你眼前最新的一句话。
3. 问：新建会话的最佳时机是什么？答：当问题边界变了，或你不再信任旧上下文时。
4. 问：什么时候复用旧会话更合适？答：当你需要引用先前推理、附件或工具结果时。
5. 问：为什么长期保留所有会话会产生问题？答：列表会变乱，回溯成本上升，也更难判断哪些线程仍有价值。
6. 问：如何判断一个会话是否值得继续？答：看它是否仍围绕同一目标、同一角色和相近资料边界。
7. 问：什么情况下应该创建分支而不是重写问题？答：当你想尝试另一条方案，但又不想丢掉当前线程的结果。
8. 问：分支对话的真正价值是什么？答：保留主线结论的同时，允许平行实验不同路径。
9. 问：为什么分支比复制粘贴旧消息更好？答：分支天然保留上下文，不需要手工迁移历史。
10. 问：什么时候编辑上一条用户消息比继续追问更合理？答：当上一条提示本身有结构性错误，而不是仅仅缺少补充信息。
11. 问：为什么错误提示词应该优先编辑而不是连续补丁？答：连续补丁会让线程越来越扭曲，模型难以聚焦原始目标。
12. 问：消息置顶适合什么内容？答：关键约束、最终结论、固定格式要求和后续必须遵守的上下文。
13. 问：为什么不是所有好回答都该置顶？答：置顶过多会稀释真正重要的锚点。
14. 问：如何清理无价值线程？答：保留有复用价值的会话，其余应尽快归档思路到 Documents 或直接放弃。
15. 问：什么时候应该把会话沉淀到 Documents？答：当输出已经变成长期知识，而不是一次性对话结果。
16. 问：会话标签页的价值是什么？答：让多个任务保持并行而不互相污染。
17. 问：为什么多标签也会出问题？答：标签越多，注意力切换成本越高，也越容易发错线程。
18. 问：如何降低发错线程的风险？答：给会话明确命名，并在发送前看一眼当前 Agent 和模型。
19. 问：会话命名为什么重要？答：它直接影响你后续能否快速找回任务脉络。
20. 问：一个好会话标题应包含什么？答：目标、主题或任务阶段，而不是泛泛的“测试”“新对话”。
21. 问：什么时候应该结束一个线程？答：当目标已经完成，或它已经偏离到不值得再修补的程度。
22. 问：为什么“继续追问直到对”为常见坏习惯？答：因为很多时候问题不是追问深度，而是会话结构已经失真。
23. 问：如何判断上下文已失真？答：模型开始反复引用旧限制、答非所问，或一直围绕历史噪声打转。
24. 问：会话和 Agent 绑定是永久的吗？答：不是，会话内可以切换 Agent，但切换前要意识到角色会变。
25. 问：切换 Agent 后为什么有时结果更乱？答：因为旧上下文仍然存在，而新 Agent 的系统提示会重新解释它。
26. 问：什么情况下切 Agent 是好策略？答：当前角色明显不适合任务，但上下文事实仍有复用价值。
27. 问：什么情况下应新建会话而非切 Agent？答：当角色切换连任务语境都需要重建时。
28. 问：会话和模型切换哪个影响更大？答：两者影响不同；模型改能力，Agent 改行为边界，二者都可能是主因。
29. 问：这一轮会话管理最重要的原则是什么？答：不要把“历史越多越好”误当成“上下文越完整越强”。
30. 问：线程管理的最终目标是什么？答：让每个会话都保持单一任务方向、可回溯、可接续、可结束。

## 第 3 轮：提问与输入组织

1. 问：为什么同一个模型会因为提问方式不同而差异巨大？答：因为输入结构直接影响模型如何分配注意力与推理路径。
2. 问：一个好问题的最小组成是什么？答：目标、上下文、限制、输出要求。
3. 问：为什么目标要先说？答：模型先知道终点，才知道哪些信息重要。
4. 问：为什么上下文不能无限堆？答：过多上下文会稀释真正关键的信息密度。
5. 问：什么时候应该分段输入？答：当你同时要求背景、约束、任务和格式时。
6. 问：为什么格式要求值得显式写出？答：否则模型会默认输出它常见但不一定适合你的格式。
7. 问：什么情况下应该要求表格？答：对比、选型、风险列表和状态汇总时。
8. 问：什么情况下不应该要求表格？答：需要长解释、叙事推理或自由结构时。
9. 问：为什么限制条件必须明确？答：模型不会天然知道哪些方案你明确不接受。
10. 问：常见限制有哪些？答：语言、长度、技术栈、风险边界、时间范围、输出格式。
11. 问：为什么“简单点”这种要求经常无效？答：它太模糊，没有告诉模型要删掉什么。
12. 问：怎样写“简单点”才有效？答：说明保留什么、删掉什么、字数或结构压缩到什么程度。
13. 问：为什么“帮我分析一下”经常得到平庸回答？答：它没有说明分析对象、分析维度和决策用途。
14. 问：什么情况下应该先问模型“你还缺什么信息”？答：当任务明显依赖关键前置条件，而你不确定是否已经给足。
15. 问：什么时候该先给例子？答：当你要求特定风格、格式或边界时。
16. 问：例子应该多长？答：只给足够说明模式的最短例子，不要喧宾夺主。
17. 问：为什么反例也有价值？答：它能快速收窄模型的输出空间。
18. 问：什么时候应该分多轮提问？答：当问题太复杂，单轮会混合澄清、设计、执行和评估。
19. 问：为什么多轮提问通常比一条超长 prompt 更稳？答：多轮能逐步校准，而不是一次性赌运气。
20. 问：什么情况下需要要求模型先列假设？答：当输入存在明显不确定性，而错误假设会影响结论。
21. 问：为什么“先列假设再回答”有时特别有用？答：它能暴露模型是否已经误解问题。
22. 问：什么时候该让模型先给大纲？答：当输出较长、后续还要继续修改时。
23. 问：为什么先要大纲再要正文更稳？答：你能先纠偏方向，再让模型展开细节。
24. 问：什么情况下应该把约束写成编号列表？答：当约束超过两三条时，编号更容易被稳定遵守。
25. 问：为什么输入里的顺序会影响输出？答：模型往往优先响应越靠前、越明确的指令。
26. 问：什么时候该把最终要求放在结尾重申？答：当中间上下文很多，怕模型在末尾丢焦点时。
27. 问：怎样判断输入已经过载？答：你自己回看都难快速抓住重点时，模型通常也会被稀释。
28. 问：为什么提问不是“越礼貌越好”，而是“越清楚越好”？答：礼貌不替代信息结构，真正重要的是目标清晰度。
29. 问：这一轮最该训练的习惯是什么？答：每次输入前先问自己：目标、边界、格式是否都写清楚了。
30. 问：输入组织的最终目标是什么？答：让模型尽量少猜、少跑偏、少浪费上下文容量。

## 第 4 轮：Agent 选择与角色控制

1. 问：为什么同一问题换 Agent 会明显变样？答：因为 Agent 的系统提示、技能和权限边界都变了。
2. 问：什么时候应该先用 Assistant？答：当你还不确定任务最终归属，想先获得一个中性起点时。
3. 问：什么时候应该用 Code Expert？答：当问题中心是代码实现、调试、架构或工程判断。
4. 问：什么时候应该用 Writing Strategist？答：当你要的是表达质量、结构清晰度和受众匹配。
5. 问：什么时候应该用 Research Analyst？答：当你更关心问题拆解、资料比较和不确定性提示。
6. 问：什么时候应该用 Security Auditor？答：当任务需要风险识别、攻击面判断和最小缓解建议。
7. 问：什么时候应该用 Data Analyst？答：当核心工作是解释指标、整理数据和提出分析结论。
8. 问：什么时候应该用 DevOps Expert？答：当任务涉及部署、日志、CI、基础设施或回滚路径。
9. 问：为什么 Pipeline builder 不该拿来直接做业务任务？答：它的职责是编排流程，而不是替你完成终局内容。
10. 问：Agent builder 的正确用法是什么？答：用来生成或调整 Agent 配置，而不是替代普通任务执行。
11. 问：Timer builder 的正确用法是什么？答：把自然语言需求变成定时器结构，而不是直接给出最终业务答案。
12. 问：Document editor 的正确场景是什么？答：当结果必须落实到已保存文档，而不是只停留在聊天回复。
13. 问：Channel builder 的正确场景是什么？答：当你需要配置渠道对象和回复 Agent，而不是直接处理消息内容。
14. 问：为什么专业 Agent 常比通用 Agent 更稳定？答：职责越窄，提示词与技能越容易对齐。
15. 问：为什么专业 Agent 也可能答得更差？答：如果任务超出了它的角色边界，它会被系统提示限制住。
16. 问：什么时候该切换 Agent 而不是重写 prompt？答：当问题不在提问方式，而在角色选错了。
17. 问：什么时候重写 prompt 比换 Agent 更合适？答：当当前角色对，但任务说明过于模糊。
18. 问：为什么 Agent 选择是一种“路由”而不是“皮肤切换”？答：因为它改变的不只是语气，还有运行策略。
19. 问：为什么技能绑定会影响 Agent 选择？答：有些 Agent 因为绑定了特定技能，在某领域表现更稳定。
20. 问：什么情况下应该复制一个 Agent 自己改？答：当现有 Agent 接近你要的角色，但边界、格式或权限还需要收紧。
21. 问：为什么不要盲目创建大量新 Agent？答：Agent 越多，选择成本、维护成本和角色重叠也越高。
22. 问：一个坏 Agent 最常见的问题是什么？答：职责过宽、提示过长、限制不清。
23. 问：如何判断 Agent 问题来自提示词还是模型？答：换模型不换 Agent、或换 Agent 不换模型做最小对比。
24. 问：为什么 Agent 测试应该在模块内先做？答：这样能先隔离角色问题，再放回正式会话。
25. 问：切 Agent 后是否应该重读会话历史？答：应该，因为新 Agent 会重新解释旧上下文。
26. 问：为什么同一个 Agent 在新会话里可能比旧会话里更好？答：因为干净上下文让系统提示更容易主导结果。
27. 问：Agent 和工具权限是什么关系？答：Agent 可决定允许什么工具参与该类任务。
28. 问：为什么高权限 Agent 不应默认用于一切任务？答：权限越宽，出错或误调用工具的风险越大。
29. 问：这一轮选择 Agent 的核心原则是什么？答：优先选职责最贴近、边界最清楚的 Agent。
30. 问：Agent 选择的最终目标是什么？答：让正确角色以最少纠偏成本完成正确任务。

## 第 5 轮：模型选择与能力判断

1. 问：为什么 Agent 选对了仍可能答不好？答：因为底层模型能力、速度或上下文长度不匹配。
2. 问：选择模型时第一看什么？答：先看任务类型，而不是只看模型名气。
3. 问：复杂推理任务更看重什么？答：看稳定推理能力、上下文容量和格式遵循。
4. 问：快速草稿任务更看重什么？答：看延迟、成本和足够可接受的质量。
5. 问：本地模型最适合什么？答：隐私优先、离线可用或低成本试验场景。
6. 问：为什么本地模型不一定适合所有 Chat 任务？答：某些复杂推理、长上下文或模态能力可能不足。
7. 问：云模型最常见优势是什么？答：整体能力更强、更新更快、模态支持更广。
8. 问：云模型最常见代价是什么？答：成本、网络依赖和凭据管理复杂度更高。
9. 问：OpenAI-compatible 类型最适合什么？答：私有网关、自建代理和兼容协议的平台接入。
10. 问：为什么同一个 provider 下也要比较不同 model？答：同一厂商不同模型的成本、延迟和遵循度差异可能很大。
11. 问：什么时候该优先低成本模型？答：在探索、草稿和大量重复任务阶段。
12. 问：什么时候该切到高能力模型？答：在关键总结、长资料综合和高风险决策支持阶段。
13. 问：为什么不要用最强模型处理所有任务？答：成本和响应时间通常都不划算，也未必带来明显收益。
14. 问：如何判断当前模型不合适？答：经常跑偏、上下文丢失、格式不稳或成本过高时就该怀疑它。
15. 问：为什么模型切换要和任务类型绑定？答：因为模型优势通常是任务相关的，而不是全局绝对优劣。
16. 问：会话中途换模型有什么风险？答：输出风格和理解方式会变化，旧上下文可能被新模型重新解释。
17. 问：会话中途换模型什么时候值得？答：当前模型明显不胜任，但你仍想复用已有线程事实时。
18. 问：为什么“回答慢”不一定是坏事？答：复杂任务在更强模型上可能本来就需要更高推理成本。
19. 问：为什么“回答快”也不一定是真正高效？答：如果之后要不断重试和纠偏，整体效率反而更差。
20. 问：如何比较两个模型是否适合当前 Chat 任务？答：用同一问题、同一 Agent、同一上下文进行对比。
21. 问：比较模型时最该观察哪些维度？答：正确性、结构稳定性、速度、成本、引用质量和工具配合度。
22. 问：为什么要看工具配合度？答：Chat 并不总是纯文本任务，模型如何处理工具调用很关键。
23. 问：附件类任务的模型选择应额外看什么？答：看输入模态是否支持，处理稳定性如何。
24. 问：长文档聊天时模型选择应额外看什么？答：看上下文窗口和长内容压缩能力。
25. 问：为什么有时低成本模型也足够？答：如果任务边界窄、资料清晰、格式简单，它完全能胜任。
26. 问：为什么有时高能力模型仍然失败？答：因为失败可能来自上下文污染、角色选错或输入结构差。
27. 问：模型问题与 Agent 问题怎么区分？答：固定一个只换另一个，做最小变量对比。
28. 问：这一轮模型选择最关键的原则是什么？答：模型要服务任务，不要让任务去迁就模型名气。
29. 问：什么时候该回到 Models 模块而不是继续在 Chat 里调？答：当问题已经是连通性、启用状态或 provider 配置层面的故障。
30. 问：模型选择的最终目标是什么？答：以合适的成本和稳定性完成合适的任务。

## 第 6 轮：附件、资料与上下文注入

1. 问：为什么附件不是“上传完就好”？答：模型还需要知道你希望如何处理它们。
2. 问：附件进入 Chat 前第一件事是什么？答：确认当前模型支持对应输入类型。
3. 问：为什么支持图片的模型不一定也擅长文件总结？答：模态支持和任务质量并不是同一件事。
4. 问：上传附件后应补什么说明？答：说明你要提取什么、分析什么、输出成什么格式。
5. 问：为什么“帮我看看这个文件”通常不够？答：它没有告诉模型你关心的信息维度。
6. 问：图片附件最常见的好用场景是什么？答：界面截图解读、图表阅读、视觉错误定位。
7. 问：文件附件最常见的好用场景是什么？答：摘要、结构提取、差异对比、问题清单整理。
8. 问：音频附件最常见的好用场景是什么？答：语音记录整理、要点提取和会话归纳。
9. 问：附件为什么不该无差别堆很多？答：上下文容量有限，且不同附件之间会互相分散注意力。
10. 问：什么时候多个附件仍值得一起送？答：当任务明确要求交叉比较或合并总结时。
11. 问：什么时候应拆成多轮附件任务？答：当每个附件都足够复杂，混在一起会大幅降质时。
12. 问：Documents 和附件的边界是什么？答：一次性临时输入用附件，长期知识区用 Documents。
13. 问：为什么长期资料更适合进 Documents？答：这样可以保存结构、回链和后续复用语义。
14. 问：什么时候应该把附件转成文档再聊？答：当这份资料会被反复引用或需要长期维护时。
15. 问：如何让模型严格基于附件回答？答：显式要求“仅基于附件内容回答，并说明缺失信息”。
16. 问：为什么要允许模型说“不足以判断”？答：否则它更容易为了迎合你而过度推测。
17. 问：上下文注入和附件上传有什么区别？答：附件是本轮输入对象，上下文注入更像长期工作材料的选取。
18. 问：文档上下文为什么不能全选？答：全选会稀释相关内容并增加泄露或跑偏风险。
19. 问：选文档上下文时最该看什么？答：相关性、时效性和敏感性。
20. 问：为什么越多上下文不一定越准确？答：上下文一旦过载，模型会更难判断真正的关键证据。
21. 问：什么情况下该先让模型总结资料再继续任务？答：资料长而杂时，先压缩上下文通常更稳。
22. 问：为什么“先总结再执行”是好策略？答：你可以先确认模型理解了资料，再进入下一步任务。
23. 问：附件和工具调用有什么关系？答：某些任务可能需要先解析附件，再触发工具执行下游动作。
24. 问：为什么敏感附件要特别谨慎？答：它们不仅影响本轮输出，也可能通过上下文扩散到后续任务。
25. 问：什么时候应该先去 Settings 再处理附件？答：当文件系统、工具确认或安全边界还没配清楚时。
26. 问：附件任务失败时先查什么？答：模型模态支持、附件本身质量、任务说明和上下文拥挤度。
27. 问：为什么同一附件换个提示就可能好很多？答：因为模型知道“看什么”比“看到什么”更关键。
28. 问：这一轮处理资料的核心原则是什么？答：上下文和附件都应该服务任务，而不是作为信息倾倒桶。
29. 问：什么时候应该从 Chat 退出去整理资料？答：当你发现问题本质是知识结构差，而不是回答能力差。
30. 问：附件与上下文注入的最终目标是什么？答：把真正相关的信息以最低噪声方式送到模型面前。

## 第 7 轮：工具调用与执行观察

1. 问：为什么 Chat 里要看工具调用而不只看最终回答？答：因为过程决定答案是否可信、是否可复现。
2. 问：工具调用展示的主要价值是什么？答：让你知道 Agent 为了完成任务实际做了什么。
3. 问：什么时候工具调用是好事？答：当任务本身就需要真实环境、文件、搜索或外部系统能力时。
4. 问：什么时候工具调用反而是风险信号？答：当任务本不需要工具，却被高权限 Agent 过度扩展时。
5. 问：为什么工具调用能帮助你判断 Agent 是否选对？答：因为错误的 Agent 往往会调用错误类型的工具。
6. 问：看工具事件时第一看什么？答：看是否真的调用了你预期的能力。
7. 问：第二看什么？答：看调用顺序是否合理。
8. 问：第三看什么？答：看结果是否支撑了最终回答，而不是成为无关噪声。
9. 问：为什么“成功调用了工具”不等于“任务完成了”？答：工具调用只是过程节点，结果仍可能错误解释。
10. 问：什么时候应怀疑工具结果被模型误读？答：当最终结论和工具原始结果明显不一致时。
11. 问：为什么要保留工具事件的可见性？答：否则用户只能盲信最终输出。
12. 问：工具调用失败最常见的根因是什么？答：权限不足、环境不对、参数不对或目标对象不存在。
13. 问：为什么失败后不应立刻无限重试？答：如果根因不变，重试只是重复浪费。
14. 问：什么时候可以合理重试？答：当错误明显来自短暂网络波动或瞬时外部故障时。
15. 问：什么时候应先回到 Settings？答：当错误根因已经是工具确认、安全策略或目录允许列表。
16. 问：什么时候应先回到 Agents？答：当问题来自工具白名单、黑名单或权限模式。
17. 问：什么时候应先回到 Models？答：当问题来自模型根本没能稳定触发工具链。
18. 问：为什么工具调用顺序会影响结果？答：很多任务要求先取证据，再加工，再输出，顺序错了就会跑偏。
19. 问：为什么需要知道“工具调用了什么”而不是只看“有没有调”？答：是否使用了正确工具和是否使用工具本身一样重要。
20. 问：什么时候工具调用太多本身就是问题？答：当简单任务被拆成很多无意义操作，说明 Agent 或 prompt 有问题。
21. 问：如何判断工具链是否过度？答：看调用是否真正贡献信息，还是只是重复确认同一事实。
22. 问：为什么通用 Assistant 更容易在工具上过度发散？答：因为职责更宽，若限制不清就更容易多做无关动作。
23. 问：专业 Agent 的工具优势是什么？答：更容易把工具调用集中在和任务真正相关的范围内。
24. 问：工具事件对审计价值是什么？答：它让你能够回看任务为何得出某个结论。
25. 问：为什么工具结果也需要上下文判断？答：原始结果可能是局部事实，不一定等于最终决策本身。
26. 问：什么情况下应该要求模型“先展示工具发现，再下结论”？答：当你需要显式验证证据链时。
27. 问：什么时候完全不希望工具参与？答：纯思考、纯改写、纯结构整理等不依赖外部状态的任务。
28. 问：这一轮最核心的观察习惯是什么？答：把工具调用当作证据链，而不是聊天动画。
29. 问：如果用户只关心结果，为什么你仍该关注工具过程？答：因为结果一旦错，过程是唯一能快速定位根因的线索。
30. 问：工具观察的最终目标是什么？答：让执行既可解释、又可控、还可复盘。

## 第 8 轮：输出质量、追问与收口

1. 问：为什么拿到第一版回答后不应立刻结束？答：第一版通常只能验证方向，不一定已经达到交付质量。
2. 问：第一眼看回答先看什么？答：先看有没有回答你真正的问题。
3. 问：第二眼看什么？答：看结构是否便于下一步使用。
4. 问：第三眼看什么？答：看有没有明显越界、遗漏或臆测。
5. 问：什么叫“回答了但没解决”？答：解释很多，却没有把输出收敛成可执行结果。
6. 问：什么时候该要求重写而不是继续追问？答：当整体结构、角度或格式都不对时。
7. 问：什么时候追加一轮追问更合适？答：当方向对，但缺少局部细节、排序或约束。
8. 问：为什么“请更详细”不总是有用？答：它没有说明要展开哪一部分。
9. 问：怎样追问更高效？答：点名具体段落、具体维度和具体输出变化。
10. 问：什么时候应该让模型自检？答：当你怀疑它遗漏约束、冲突条件或格式规范时。
11. 问：为什么“请检查是否遗漏 X”比“再检查一下”更有效？答：它明确了检查目标。
12. 问：什么时候应该让模型给出多个方案？答：当你还在选路径，而不是进入执行阶段。
13. 问：什么时候不该要求多个方案？答：当你其实已经明确要一个收敛答案时。
14. 问：为什么方案太多会降低可用性？答：它会把决策压力重新丢回给你。
15. 问：什么时候应该要求模型排序？答：当输出是备选项而你需要优先级时。
16. 问：为什么排序要写清依据？答：否则模型可能按它自己的隐含标准排序。
17. 问：什么时候应该要求结论先行？答：当你要快速决策，不想先读完整过程时。
18. 问：什么时候应该要求过程先行？答：当你更关心推理路径是否成立时。
19. 问：为什么输出结构应该随着任务改变？答：因为“解释”“决策”“执行清单”“摘要”不是同一种结果物。
20. 问：什么时候应该让模型给 checklist？答：当你要落地执行或交给别人跟进时。
21. 问：什么时候应该让模型给风险表？答：当你要评估方案边界和失败代价时。
22. 问：什么时候应该让模型改成邮件/报告/文档风格？答：当输出不再是给自己看，而是要交付给他人。
23. 问：为什么 Chat 输出有时该立即转入 Documents？答：当它已经成了长期资产，而不是临时对话结果。
24. 问：什么时候应把输出转成 Pipeline 输入？答：当你已经发现这是一类可重复的执行模板。
25. 问：什么情况下应该停止继续优化回答？答：当边际收益已经低于继续聊天的成本。
26. 问：如何判断已经“够好”？答：结果可以直接被执行、复述或转交，而无需再补大量解释。
27. 问：为什么过度优化回答会浪费成本？答：你可能在打磨并不会长期复用的临时结果。
28. 问：这一轮最关键的问题是什么？答：这份回答现在能不能被真正使用。
29. 问：Chat 结果最理想的终点是什么？答：要么进入行动，要么进入文档，要么进入自动化，不再悬空。
30. 问：输出收口的最终目标是什么？答：把对话结果转换成真正有后续价值的产物。

## 第 9 轮：故障排查与恢复路径

1. 问：Chat 没回复时第一步是什么？答：先确认消息是否真正发送，而不是立刻怀疑所有系统都坏了。
2. 问：如果消息发了但一直卡住，先查什么？答：先查模型连接和 provider 状态。
3. 问：为什么要先查 Models 而不是先骂 Agent？答：模型不可用时，Agent 再好也无从发挥。
4. 问：模型连得上但回答总失败，下一步查什么？答：查当前模型是否启用、是否选对、是否有权限问题。
5. 问：工具调用报错时先去哪？答：先看当前 Agent 的工具权限和 `Settings -> Security`。
6. 问：为什么 Settings 在 Chat 故障里经常是根因？答：因为全局工具、安全和目录规则都在那里。
7. 问：什么时候 Logs 比 Chat 界面更重要？答：当现象重复出现，但界面上没有足够解释时。
8. 问：为什么有些故障只看 Chat 永远定位不到？答：因为真正错误发生在 provider、工具、预加载桥或外部运行层。
9. 问：当回复明显答非所问时，先查哪类问题？答：先查会话上下文是否已经被污染。
10. 问：为什么上下文污染会像“模型变笨”一样？答：因为模型会被旧线程约束拖偏，而不是能力突然下降。
11. 问：如何快速验证是否是上下文污染？答：用同一问题在新会话里复跑一次。
12. 问：如果新会话变好，说明什么？答：说明旧线程本身就是主要问题源。
13. 问：如果新会话仍不好，说明什么？答：更可能是模型、Agent 或输入结构层的问题。
14. 问：如何区分 Agent 问题和模型问题？答：固定一个变量，只换另一个做对照。
15. 问：如何区分输入问题和系统问题？答：用一个极小、极明确的问题做健康检查。
16. 问：如果极小问题都不稳定，意味着什么？答：更可能是模型或环境层面故障。
17. 问：如果极小问题稳定，复杂问题失真，意味着什么？答：更可能是上下文、Agent 或 prompt 结构问题。
18. 问：附件问题如何排查？答：先查模态支持，再查附件质量，再查任务说明。
19. 问：文档上下文问题如何排查？答：先减少文档数量，只保留最相关内容再复测。
20. 问：工具过度调用如何排查？答：先换窄职责 Agent，或明确要求“不使用工具，先纯分析”。
21. 问：工具完全不调用如何排查？答：先看权限，再看任务是否真的需要工具，再看模型是否支持该链路。
22. 问：为什么复盘失败线程有价值？答：同类失败往往会重复出现，记录模式能降低后续排障时间。
23. 问：什么时候应从 Chat 直接跳去 Pipeline 历史？答：当失败来自由 Chat 触发的流水线任务。
24. 问：什么时候应从 Chat 直接跳去 Channels？答：当这条任务实际来自外部渠道而不是桌面会话。
25. 问：什么时候应从 Chat 直接跳去 MCP？答：当任务依赖外部协议化能力，而该能力疑似不可用时。
26. 问：为什么排障时要缩小变量？答：因为同时改模型、Agent、prompt 和上下文只会让问题更难定位。
27. 问：恢复路径的第一原则是什么？答：从最便宜、最能排除大片可能性的检查开始。
28. 问：恢复路径的第二原则是什么？答：一旦确认根因所属层级，就回到那个模块修，不要继续在 Chat 里硬拗。
29. 问：恢复路径的第三原则是什么？答：修复后立刻用最小任务复测，而不是直接跳回复杂场景。
30. 问：排障的最终目标是什么？答：快速分层定位，把 Chat 问题还原到正确的根因模块。

## 第 10 轮：安全、沉淀与长期迭代

1. 问：为什么 Chat 不是无风险的对话框？答：因为它可能触发真实工具、外部系统和敏感资料流动。
2. 问：Chat 中最常见的风险源是什么？答：宽权限 Agent、敏感附件和不受控的工具调用。
3. 问：为什么默认用高权限 Agent 是坏习惯？答：任务一旦走偏，风险会同步放大。
4. 问：什么时候必须特别警惕敏感资料？答：当你要上传文件、注入 Documents 上下文或让工具访问本地资源时。
5. 问：为什么“只是聊天”也可能有安全后果？答：因为聊天现在常常是工具和系统能力的调度面。
6. 问：如何降低误操作风险？答：优先使用边界清晰、权限较窄的 Agent 和最小上下文。
7. 问：为什么资料越敏感越该先想结构再输入？答：因为一旦送进上下文，就可能影响后续多轮任务。
8. 问：什么时候该明确要求“不调用工具”？答：当你只需要推理、改写、总结或方案比较时。
9. 问：什么时候该明确要求“如需工具先说明”？答：当任务可能越过你对执行边界的预期时。
10. 问：为什么确认工具调用路径是一种治理手段？答：它让 AI 执行从黑盒变成可审查流程。
11. 问：为什么 Chat 结果不应全部停留在会话里？答：长期有价值的内容需要沉淀到文档或自动化资产中。
12. 问：什么时候该把高价值回答转成 Documents？答：当它会被团队复用、稍后再看或成为知识基线。
13. 问：什么时候该把成功对话转成 Agent 调整？答：当你发现某类任务总要重复写同样的约束。
14. 问：什么时候该把成功对话转成 Skill？答：当它体现的是可复用领域规则，而不是单个角色特性。
15. 问：什么时候该把成功对话转成 Pipeline？答：当它已经清楚暴露出一组可重复步骤。
16. 问：什么时候该把成功对话转成 Timer？答：当该任务不仅可重复，还需要固定节奏执行。
17. 问：为什么 Chat 是发现工作流的地方，而不是工作流的终点？答：因为对话最适合探索，稳定结构应转入其他模块。
18. 问：长期使用 Chat 后最容易出现什么问题？答：会话泛滥、角色混乱、上下文污染和重复劳动。
19. 问：如何避免会话泛滥？答：定期结束线程、统一命名、把长期资产转出聊天区。
20. 问：如何避免角色混乱？答：给任务选最合适 Agent，而不是让一个 Agent 扛所有问题。
21. 问：如何避免上下文污染？答：敢于新建会话、分支会话、压缩上下文和减小文档注入范围。
22. 问：如何避免重复劳动？答：把稳定约束写进 Agent、Skill、Pipeline 或 Documents。
23. 问：为什么每次成功对话都值得问“能不能沉淀”？答：因为真正的效率提升来自沉淀，而不是一次次从零开始。
24. 问：为什么每次失败对话也值得复盘？答：失败模式同样能转化为 Agent 收敛、技能约束或安全规则。
25. 问：Chat 长期治理最该关注什么指标？答：线程可找回性、角色稳定性、输出可复用性和失败定位速度。
26. 问：为什么输出可复用性很重要？答：一次对话价值有限，可复用资产才能累积效率。
27. 问：为什么失败定位速度也算治理指标？答：排障越快，说明模块边界和使用策略越清楚。
28. 问：长期来看 Chat 最好的状态是什么？答：它既是高效入口，又不会吞掉本应沉淀到其他模块的资产。
29. 问：这份深挖手册最大的目的是什么？答：让你把 Chat 用成受控工作台，而不是随机问答窗口。
30. 问：Chat 长期迭代的最终目标是什么？答：把探索、执行、沉淀和治理连成一条可持续的工作路径。
