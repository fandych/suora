# 应用架构

SUORA 是一个 Electron 桌面端 AI 工作台。当前架构以 **Renderer / Preload / Main process** 的进程边界为核心：React 渲染进程负责界面与交互，preload 负责暴露受控 bridge，Electron 主进程负责数据库、网络、文件、命令、浏览器工具和各类运行时。

## 当前目录结构

```text
src/
├── App.tsx
├── main.tsx
├── components/
│   └── ui/
├── pages/
├── services/
├── stores/
├── hooks/
├── lib/
├── types/
├── drizzle/
└── electron/
    ├── main.ts
    ├── preload.ts
    ├── app/
    ├── infrastructure/
    └── preload/
```

与旧版结构相比，当前仓库**不再使用** `src/views/`、`src/application/`、`src/domain/`、`src/data/domain/`、`src/data/repositories/` 或 `electron/application/` 这类层。新增代码应落在现有目录中，而不是继续扩展这些旧抽象。

## 进程分层

## Renderer

Renderer 由 React、React Router、Zustand 和页面级组件组成，主要位于：

- `src/pages/`：路由页面与页面级组件
- `src/components/`：全局业务组件和 `ui/` primitives
- `src/services/`：封装 `window.app` 的 renderer facade
- `src/stores/`：UI 状态、缓存与运行时协同
- `src/lib/`：浏览器端工具、导出、聊天展示与序列化辅助

Renderer 不直接访问 SQLite、文件系统、命令执行、Electron 原生 API 或主进程 repository。页面通常经 `src/services/` 调用 `window.app` 暴露的 bridge，再由 store 或页面消费结果。

## Preload

`src/electron/preload.ts` 在 `contextIsolation: true` 下暴露两类入口：

- `window.app`：面向业务域的稳定方法，例如 `chats`、`documents`、`models`、`workflows`、`preferences`
- `window.electron`：少量受白名单限制的低层 `invoke/on/off` 能力，主要用于流式 AI、workflow runtime、渠道消息和浏览器状态等事件

按业务域注册 `ipcMain.handle` 的代码位于 `src/electron/preload/`。这一层只做：

1. 输入校验
2. 边界授权
3. 调用主进程应用服务
4. 返回可序列化 DTO 或转发事件

它不应承载页面逻辑，也不应在这里堆放大块业务规则。

## Main process

主进程入口是 `src/electron/main.ts`。当前启动流程包括：

1. 配置应用存储路径
2. 确保 workspace 目录存在
3. 打开 SQLite 并执行 migration
4. 初始化主进程应用服务
5. 注册 IPC
6. 注册 renderer protocol、自动更新和窗口

业务逻辑位于 `src/electron/app/`，平台与运行时基础设施位于 `src/electron/infrastructure/`。

## 主进程业务域

`src/electron/app/` 按业务域组织，当前重点包括：

- `agents`
- `channels`
- `chats`
- `documents`
- `integrations`
- `models`
- `preferences`
- `schedulers`
- `skills`
- `system`
- `tools`
- `workflows`

每个业务域负责自己的 service、repository、runtime 或执行器，而不是把逻辑堆到全局 service 目录。

## 数据流

典型的数据流如下：

```text
React page / store
  → src/services/<module>-service.ts
  → window.app.<domain>.<method>
  → electron/preload/<domain>/*-ipc.ts
  → electron/app/<domain>/service.ts
  → repository / runtime / infrastructure
  → serialized result or event
```

当能力需要流式事件时，会额外经过 `window.electron.on/off` 的白名单事件通道，例如：

- `ai:fetch:event`
- `workflow:run:event`
- `channel:message`
- `tools:browserStateChanged`

## 数据与持久化

SUORA 使用 Node `node:sqlite` 的 `DatabaseSync` 与 Drizzle schema。相关代码位于：

- `src/drizzle/schema/`
- `src/drizzle/migrations/`
- `src/electron/infrastructure/db-core.ts`

数据库文件默认位于：

```text
<Electron userData>/workspace/suora.sqlite
```

Renderer 不暴露任意 SQL bridge。跨进程使用的请求/响应契约集中放在 `src/types/`。

## 路由与模块

主应用的一级路由当前为：

- `/chats`
- `/agents`
- `/workflows`
- `/schedulers`
- `/integrations`
- `/documents`
- `/channels`
- `/skills`
- `/models`
- `/preference/:section`

根路径重定向到 `/chats`。新 UI 和新文档统一使用 `workflow` / `workflows` 命名；只有在兼容旧实现或迁移说明中才提及 `pipeline`。

## 安全边界

- 主窗口：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: false`
- Browser 工具窗口：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`
- 所有敏感操作都应由主进程重新校验，而不是信任 Renderer 状态
- 凭据、命令、文件访问、URL 与集成执行均由主进程作为最终安全边界

当前没有多用户权限模型；本地安全最终仍依赖操作系统账户、设备权限和数据库/凭据文件保护。

## 架构维护原则

1. **数据和副作用靠近主进程**：数据库、网络、文件、命令、浏览器与凭据处理留在 `src/electron/`。
2. **展示和交互靠近 Renderer**：页面、组件、store 与 renderer service 不直接越权。
3. **跨边界契约集中管理**：复用类型放在 `src/types/`，不要散落在页面或 handler 中。
4. **优先扩展现有业务域**：新能力先放入现有 `electron/app/<module>/`，避免创建模糊层。
5. **文档跟随实际代码**：架构变化后，同时更新本页以及相关技术/用户文档。
