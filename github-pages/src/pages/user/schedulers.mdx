# Schedulers

Schedulers 用于保存面向 workflow 或 Agent 的 cron、时区、输入和重试策略配置。它适合先定义和维护自动化计划，但当前版本仍是**本地持久化的调度配置编辑器**，不是已经运行的定时执行引擎。

## 创建调度配置

1. 在 **Schedulers** 模块的二级侧边栏选择 **New scheduler**。
2. 在左侧 **General** 面板填写名称、描述、cron 表达式、时区及重试策略。
3. 在右侧 **Binding** 面板选择目标类型：workflow 或 Agent，再选择目标。
4. 若绑定 workflow，按 workflow 起始节点声明的输入字段填写参数；若绑定 Agent，填写每次触发时发送给 Agent 的任务提示词与上下文。
5. 使用 Enabled 开关保存为启用或暂停状态。

新建 Scheduler 默认值：

| 字段 | 默认值 |
| --- | --- |
| 名称 | `New scheduler` |
| Enabled | 开启 |
| Cron | `0 9 * * *` |
| 时区 | `Asia/Shanghai` |
| 目标类型 | `workflow` |
| 错过执行策略 | `skip` |
| 重试次数 | `0` |
| 重试退避 | `300` 秒 |
| 输入 | `{}` |

列表按最近更新时间显示名称、启用状态、目标、描述和 cron；详情页的 Runtime preview 只是当前配置摘要。

详情页右上角的 **…** 菜单提供：

- **Run history**：在弹层中查看本地记录的 scheduler 运行；当前未接入的运行时会显示为空。
- **Enable / Disable**：立即保存调度配置的启用状态。
- **Delete**：删除调度配置及其本地运行历史，删除前需要确认。

## 配置字段

### Cron 与时区

cron 和时区均为文本字段。保存时只要求非空：当前不会解析 cron 语法、验证 IANA 时区名称，也不会计算下次执行时间。

建议采用标准五段 cron，并在上线前使用独立的 cron 校验工具确认语义。例如：

```text
0 9 * * *      每天 09:00
0 */6 * * *    每 6 小时
30 8 * * 1-5   工作日 08:30
```

### 目标

可选目标类型：

- **workflow**：保存某个 workflow 的 ID 和名称。
- **agent**：保存某个 Agent 的 ID 和名称。

切换目标类型时，界面会自动选择该类型的第一个可用目标。保存前要求目标 ID 非空，但不会再次验证目标仍然存在，或名称是否与真实资源一致。

<Callout>
  当前没有可用 workflow 或 Agent 时，仍可创建 Scheduler 并保存手动填写的目标 ID/名称；该配置不会自动解析或执行目标。
</Callout>

### Workflow 输入与 Agent 提示词

选择 workflow 后，Binding 面板会读取 workflow 起始节点的 input schema，并将声明的字符串、数字、布尔值、对象和数组显示为对应表单字段。表单值会保存为 `inputPayloadJson` 对象；切换 workflow 或目标类型会重置当前输入，避免将不匹配的参数传给新目标。

选择 Agent 后，Binding 面板会显示 **Invocation prompt**。它不是 Agent 的系统提示词：系统提示词仍由 Agent 本身维护；此处用于保存 scheduler 在每次触发时提供的任务、上下文或指令，并以 `{ "prompt": "..." }` 的 JSON payload 形式持久化。

输入字段为空时会保存为 `{}`；非空内容必须能被 JSON 解析。当前不会执行 Scheduler，也不会在运行期验证 schema 或 Agent payload。

### 重试与错过执行

界面提供：

- Missed-run policy：`skip` 或 `catch-up`
- Retry limit
- Retry backoff（秒）

这些字段会被保存，但当前没有非负整数、上限、策略枚举或运行期重试校验。请使用合理、保守的值，并将其作为未来运行时的设计意图。

## 重要：当前不会自动执行

当前 Schedulers **不会**：

- 解析 cron 或在到点时触发任务。
- 执行 workflow 或 Agent。
- 处理 `skip` / `catch-up` 补跑策略。
- 执行重试、退避或队列。
- 计算/显示上次运行、下次运行或运行状态。
- 生成 Scheduler 专用的运行历史、日志、失败原因或通知。
- 提供“立即运行”“取消运行”或“删除 Scheduler”操作。

<Callout type="warning">
  Enabled 仅保存为配置状态，不会启动后台定时任务。不要依赖当前 Scheduler 执行生产自动化、告警、备份、消息推送或付款流程。
</Callout>

## 推荐工作方式

1. 先在 **Workflows** 中手动验证 workflow，或在 **Chats** 中验证 Agent。
2. 再创建 Scheduler，记录期望的 cron、时区、输入与失败策略。
3. 将 Scheduler 作为未来自动化运行时的配置来源或团队约定。
4. 在真正的 cron runtime 上线前，使用外部调度器、CI、系统 cron 或受控工作流平台执行关键任务。

如果需要定时执行 workflow，目前可通过外部系统调用应用的受控入口或运行环境，但应自行处理凭据、网络可达性、重复执行、日志、告警和失败恢复。

## 当前 UI 限制

- Scheduler 可以通过二级侧边栏创建、在详情页编辑并通过 Enabled 开关暂停，但列表页没有页面级新建按钮，也不能删除。
- 没有版本、复制、导入导出或手动触发入口；Run history 仅显示未来 runtime 写入的本地记录。
- 保存失败会由调用链抛出；列表和详情加载错误可重试，但没有完整的 Scheduler 专用错误面板。
- 当前没有 Scheduler 专用测试覆盖，配置字段也没有在主进程进行完整的二次校验。

## 本地存储与安全

Scheduler 配置和运行历史分别保存在本机 SQLite 的 `schedulers`、`scheduler_runs` 表中，路径为 `<userData>/workspace/suora.sqlite`。cron、时区、目标信息和 `inputPayloadJson` 均为本地明文字段。

<Callout type="warning">
  不要把 API Key、密码、访问令牌或个人敏感信息直接放在 Scheduler 输入 JSON 中。当前没有 Scheduler 专用加密、秘密引用或字段脱敏机制。
</Callout>
